## 1. What changed this session
- **P4.3 (#46, PR #47) — propose/commit as a generic peer capability (contract-1).** A peer submits an update as a *proposal* the authority checks at apply time and either **commits** (persist-before-apply → broadcast; the proposer receives it back like a remote update) or **op-grain refuses** (a reason to the proposer, connection stays up). This is the op-grain path that **closes F-04** — the 4400 connection-grain refuse still stands for a misbehaving plain sync peer (dropping its already-self-applied op would fork it), but a peer that *wants* op-grain treatment proposes instead of self-applying.
  - **`CAP_PROPOSE`** generic capability + pure **`evaluateProposal`** (`server/db/proposeCommit.ts`): order authenticate → CAP_PROPOSE → size → decode → **injected apply-time guard**. Returns an op-grain `{commit}` / `{commit:false,reason}` decision, never a thrown close code. The guard (`ProposalGuard`) is an injected Scroll-owned Strategy; ships allow-all, the concrete spatial-band / pinned-block / lease content-hash predicate lands with the P6 doc model.
  - **Live `onStateless` seam** (`createProposeCommitExtension`): parses a Scroll proposal stateless message, evaluates, and on commit calls the injected `commitProposal`. Non-Scroll stateless traffic (Hocuspocus history-versioning `{action}`, awareness) is ignored. Wired in `server/hocuspocus.ts` sharing one `store`.
  - **F-03** — `IngressOptions.authenticate` return retyped to `{ peer: PeerIdentity }`, so a fail-open authenticator that forgets to namespace its identity is a compile error now that `server/` is typechecked. Caught the P3.6 stub (updated to conform).
  - **F-05** — admission caps are now room-authoritative: `RoomConfig.grantCaps(role)` derives them; `caps` was removed from `AdmissionRequest`, so a requester cannot self-grant (provable by construction, mirroring the `mode` removal for contract-3). `@ts-expect-error` test pins it.

## 2. Decisions made and why
- **propose/commit persists on the persistence extension's own ledger, not a side path.** The naive first cut (`store.appendUpdate` + `Y.applyUpdate` inside `onStateless`) was the adjudicator's F-01 BLOCK: Hocuspocus fires `onChange` for *every* doc update regardless of origin, and the persistence FIFO (`pendingSeqs`) assumes a 1:1 correspondence with sync-path appends. A committed proposal's phantom `onChange` (a) leaked its own row (never folded) and (b) could pop a concurrent sync peer's not-yet-applied pending seq → compaction deletes a row whose content isn't in the snapshot → **silent data loss**. Fix: `createPersistenceExtension` now returns `{ extension, commitProposal }`; `commitProposal` appends → applies (tagged `PROPOSE_ORIGIN`) → `markFoldable` directly (synchronous apply→fold, no interleave), and `onChange` early-returns on `transactionOrigin === PROPOSE_ORIGIN`. Sync FIFO untouched, proposal row folds like any write.
- **`onStateless` is crash-safe by construction.** The second F-01/F-02 BLOCK: Hocuspocus dispatches the stateless callback fire-and-forget (never awaited), so any throw — a rejected `appendUpdate` — becomes an unhandledRejection that (Node default) crashes *every* room. The whole `onStateless` body is wrapped; a commit-path failure is contained as an op-grain refusal (`'proposal rejected: commit failed'`), never rethrown.
- **Proposals ride the same 8 MiB ingress size gate.** A2 (DoS via 100 MiB stateless decode) was dismissed: `Connection.handleMessage` runs `beforeHandleMessage` (the ingress size gate) *before* dispatch for stateless frames too, so an oversized proposal frame is refused before `onStateless` ever runs.
